# ZCode Session Rescue 设计稿

日期：2026-11-18

## 目标与理由

做一个独立开源的 Python 命令行工具，从旧版 ZCode `db.sqlite` 中只恢复一个普通聊天会话到现用数据库，并支持撤销这次恢复。

现有整库合并、整库恢复、只读导出工具都没有完整覆盖这条路径。项目首先解决数据安全，不追求再做普通备份器或会话管理器。

## 使用者与成功标准

使用者是需要找回误删会话、迁移单个会话或从旧备份抢救记录的 ZCode 桌面/CLI 用户。

成功标准：

1. 默认只做预检，不改变数据库；显式传 `--apply` 才写入。
2. 每次只恢复一个明确指定的 session，不影响目标库其他会话。
3. 结构不兼容、目标已有同会话或孤立行、主键冲突、无法完整识别的关联均失败并拒写。
4. 写入前生成独立 SQLite 一致性备份和机器可读回执。
5. 撤销只删除本次插入且此后未变化的行；任何一行变化或出现依赖冲突都整体拒绝撤销。
6. 自动化测试证明失败时无部分写入，普通聊天恢复后行数和内容一致，撤销后目标库恢复到操作前状态。

## 已核实的现状

本机旧脚本 `restore-session.py` 已具备 SQLite Backup API、单事务和文本回执，但路径/session 写死、固定 12 表、使用 `INSERT OR IGNORE`，也没有精确撤销能力。

2026-11-18 对本机现用 ZCode 数据库做只读 schema 检查，发现：

- `session`、`message`、`part` 等常规聊天表。
- `todo`、`turn_usage` 等复合主键表。
- `workflow_run.parent_session_id`、`workflow_activity.child_session_id`、`session_task_link` 等跨会话/工作流关联。
- `dwf_*` 的二级关联。
- `session_runtime_presence` 等运行时状态和 `session_purge` 等删除状态。

因此不能继续把固定 12 表当作完整恢复，也不能把所有外键闭包无差别复制。

## 方案比较

### A. 独立 Python CLI（选定）

使用 Python 标准库 `argparse`、`sqlite3`、`json`、`hashlib` 和 `unittest`，无运行时第三方依赖。先完成可测试的安全内核，再考虑 exe 和 GUI。

优点：范围可控、容易审查和测试、可独立发布；缺点是首版没有图形界面。

### B. 给 zcode-import-session 贡献

可复用部分整库合并能力，但单会话选择、严格关联策略、精确撤销会改变其核心流程。首版不绑定上游方向；实现时可参考，代码复用必须遵守许可证。

### C. GUI 优先

对新手更直观，但会同时扩大界面、数据库和恢复安全测试面。推迟到 CLI 核心稳定后。

用户已把实现方式交由助手决定，因此选 A。

## 第一版范围

命令：

```text
zcode-session-rescue list --source OLD_DB [--json]
zcode-session-rescue check --source OLD_DB --session SESSION_ID --target TARGET_DB [--json]
zcode-session-rescue restore --source OLD_DB --session SESSION_ID --target TARGET_DB --operations-dir OUTPUT_DIR [--apply] [--json]
zcode-session-rescue undo --receipt RECEIPT_JSON [--apply] [--json]
```

- `list`：只读列出 session ID、标题、创建/更新时间和消息数，不输出正文。
- `check`：只读生成恢复计划，列出将复制的表、行数、跳过项和拒绝原因。
- `restore`：没有 `--apply` 时等价于 `check`；有 `--apply` 才备份并写入。
- `undo`：没有 `--apply` 时只检查能否撤销；有 `--apply` 才备份并删除。
- `--json`：输出稳定结构，便于 AI Agent 和其他工具调用。
- 目标默认不猜路径，必须显式提供，避免误操作其他 ZCode 实例。
- 源库始终使用 SQLite read-only URI 打开；目标必须已存在，工具不创建新目标库。
- 文档要求实际恢复和撤销前关闭所有可能正在写目标库的 ZCode 实例；SQLite 锁和二次行校验仍作为硬保护。

### 普通聊天恢复策略

1. 读取目标与源的 `sqlite_master`、`PRAGMA table_info`、`PRAGMA foreign_key_list`，不信任硬编码表清单。
2. 根表必须是 `session`，按 `session.id` 选中且只选中一行。
3. 自动发现含 `session_id` 的会话直属表，但排除明确的运行时/删除状态表：`session_runtime_presence`、`session_purge`。
4. 直属表必须有可定位的主键。其声明外键只能落在本次可复制的会话/消息闭包内；指向不支持实体的外键在该会话有数据时拒绝恢复。
5. `part.message_id -> message.id` 等内部依赖纳入插入顺序；事务开启外键检查，提交前任何违规都回滚。
6. 对 `parent_session_id`、`child_session_id`、`run_id` 等工作流、DWF、任务链接做存在性检查。只要选中会话涉及这些不支持关联，就拒绝恢复，不静默丢弃。
7. `session.parent_id` 指向的父会话若不在目标库中，拒绝恢复；不擅自递归恢复其他会话。
8. 对每张实际复制表要求源/目标列名、声明类型、非空约束、默认值、主键结构一致。使用显式列名插入，不依赖列顺序。 schema migration ID 只记录，不用它代替结构检查。
9. 任何无法安全分类的新表默认拒写；后续版本通过版本化适配器和真实证据扩展。

这意味着第一版只恢复普通聊天，不支持工作流、DWF、父子会话链和跨 session 任务链接。

### 冲突与事务

- 目标已有同一 `session.id`，或任一目标直属表已有该 session 的孤立行：拒绝。
- 按主键预检全局冲突；目标现有行若通过声明外键或已知语义关联反向引用任何待插入键，也按冲突拒绝，避免恢复后意外认领旧行。目标删除状态表已有同 session 记录同样拒绝。
- 写入使用普通 `INSERT`，禁止 `OR IGNORE`。
- 正式恢复时在单一源库只读事务中选定并暂存全部待复制行；回执哈希和实际 `INSERT` 只能使用这批暂存数据，禁止预检后重新读取可能变化的源行。
- 正式恢复使用 `BEGIN IMMEDIATE`，开启 `foreign_keys=ON`，必要时使用 `defer_foreign_keys=ON`，提交时仍校验。
- 在事务内重新检查 session、主键和反向引用冲突，缩小预检到写入之间发生变化造成的风险。
- 任一失败整体回滚，不生成“成功”结果。

### 备份、回执与撤销

每次实际恢复或撤销创建独立 operation 目录，目录名含操作类型、UTC 时间和随机 UUID，绝不覆盖旧操作。

恢复流程：

1. 在只读预检中计算将插入的每一行：表名、主键值、规范化的行 SHA-256。
2. 使用 SQLite Backup API 备份目标库，并校验备份可打开及 `quick_check`。
3. 在写入前保存 `receipt.json`，状态为 `prepared`，包含格式版本、operation ID、源/目标路径、schema 指纹、备份路径、行定位与哈希、行数和时间；不保存消息正文。
4. 执行事务；成功后原子更新回执为 `completed`。
5. 若进程在提交后、状态更新前退出，`undo` 可根据 `prepared` 回执与目标行哈希判断实际是否已应用，不盲目删除。

撤销流程：

1. 读取回执并校验格式、目标路径和 operation ID；可用 `--target` 显式覆盖仅用于测试/迁移的目标路径时，默认仍要求与回执一致。
2. 对回执中每一行按主键读取，并重新计算哈希。全部行仍存在且未变化时可以撤销；全部行已删除且回执处于 `undo_prepared` 时视为上次提交后崩溃，只补记 `undone`；部分缺失、内容变化或其他状态不一致均整体拒绝。
3. 创建撤销前备份，先把回执原子更新为 `undo_prepared` 并记录撤销备份，再在单事务内再次校验所有行。
4. 同时检查声明外键和已知语义关联；schema 指纹变化、出现无法分类的新关联或仍有新数据引用待删行时拒绝并回滚，不能只依赖 SQLite 外键。
5. 按依赖反序 `DELETE`，成功后把回执原子更新为 `undone`；已处于 `undone` 的回执直接拒绝重复撤销。

行哈希使用带类型标记的规范 JSON：区分 `NULL`、整数、浮点、文本、BLOB；浮点用十六进制表示，BLOB 用 Base64，避免仅拼字符串产生碰撞。复合主键完整存入回执。

文件与数据库无法组成一个原子事务，因此用预写回执、哈希验证和独立备份处理崩溃窗口，不宣称绝对无崩溃窗口。

## 非目标与反对目标

第一版不做：

- 整库合并、批量恢复、自动选择“最新”数据库。
- 工作流/DWF/父子会话树恢复。
- `tasks-index.sqlite`、rollout、artifacts 或工作区文件恢复。
- 修复物理损坏的 SQLite 数据库。
- 覆盖或合并目标中已经存在的会话。
- GUI、自动上传、云备份、遥测、自动更新。
- 在恢复后继续聊天还能无条件撤销；发生变化时拒绝撤销是预期行为。

即使技术上能运行，只要出现静默漏表、跳过冲突、无备份写入或只恢复一半仍报成功，就视为失败。

## 测试与验收

使用标准库 `unittest` 和临时目录合成最小 ZCode 数据库，不复制本机真实会话内容。

覆盖：

- 普通聊天及复合主键恢复，其他会话不变。
- 默认 dry-run 零写入。
- 已有 session、孤立行、全局主键冲突、目标反向引用待插入键均拒写。
- schema 列/类型/约束/主键不兼容均拒写。
- 工作流、DWF、父子链接及未知关联拒写。
- 运行时状态不复制。
- 插入异常时整体回滚。
- BLOB、NULL、Unicode、浮点和复合主键哈希稳定。
- 成功撤销、重复撤销拒绝、修改后撤销拒绝、声明外键及无声明外键的语义依赖新增后撤销拒绝。
- `prepared`、`undo_prepared` 回执崩溃窗口识别。
- CLI 人类可读和 JSON 输出、退出码、路径含空格/Unicode。

验收分三层：

1. 合成库自动化测试全部通过。
2. 对本机真实 ZCode 库只执行 `list`/`check` 只读验证，不做真实恢复。
3. 在真实 ZCode 中“恢复后能打开并续聊”和 GUI 体验仍需独立人工验收，自动化不得标记为已通过。

## 独立审查后的加固定案

- 外键按 `id/seq` 分组，保存删除动作；恢复闭包逐行验证，隐式主键和非主键唯一列引用都从完整行解析。
- 第一版拒绝影响恢复表的未知触发器、未识别的级联/`SET NULL` 动作、待恢复 `AUTOINCREMENT` 表和 NULL 主键组件；支持已核实的 ZCode 官方序列/删除保护触发器与官方删除动作关系。
- schema 指纹包含表 SQL 与触发器；插入后重新读取并验证每行内容。
- 行哈希按列名规范化，允许源/目标列顺序不同；父会话已有子会话时拒绝单独恢复。
- 除声明外键外，按恢复行的标识符批量检查语义引用；无法确认安全时拒写或拒绝撤销。
- 冲突与引用检查改为批量集合查询，避免按消息数乘表数逐行扫描。
- 回执在任何读写前验证操作 ID、表集合、行数、哈希、唯一性和根会话；同一目标的实际写入使用跨进程锁串行化。
- `restore` dry-run 与 `check` 使用同一份计划数据；文本输出包含时间戳和跳过表。
